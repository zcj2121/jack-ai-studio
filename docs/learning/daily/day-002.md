# Day 2：搭建最小 Monorepo 与 Web 应用骨架

## 今日目标

1. 理解 Monorepo、Workspace、App Router 和前后端边界。
2. 使用 pnpm workspace 管理 Jack AI Studio 的多个应用。
3. 初始化 `apps/web` 的 Next.js、React 和 TypeScript 基础项目。
4. 为 `apps/api` 明确职责，但不提前开发 Python API。
5. 掌握项目启动、静态检查和生产构建命令。

## 必备理论

### 1. Monorepo（单仓库多项目）

**专业解释：**

Monorepo 是在同一个 Git 仓库中管理多个相互关联的应用或包，并统一维护版本、脚本和工程规范的代码组织方式。

**大白话：**

可以把它类比成一个企业前端仓库里同时放主应用、组件库和工具包：它们住在同一个小区，但每户仍有自己的房间和职责。

**举例：**

`apps/web` 是用户界面，`apps/api` 是 Python 后端，未来 `packages/ui` 可以存放共享 UI 组件。

**在 Jack AI Studio 中的作用：**

项目最终包含 Web、API 和共享包，Monorepo 能让它们共享 Git 历史和工程命令。当前只建立最小目录，不引入 Turborepo。

### 2. Workspace（工作区）

**专业解释：**

Workspace 是包管理器提供的多包管理能力，可以在仓库根目录统一安装依赖、运行脚本，并通过包名筛选目标项目。

**大白话：**

它像小区物业：每个应用有自己的 `package.json`，根目录仍可以统一找到并管理它们。

**举例：**

`pnpm --filter @jack-ai-studio/web dev` 只启动 Web 应用，不会误启动未来的其他包。

**在 Jack AI Studio 中的作用：**

今天用 `pnpm-workspace.yaml` 声明 `apps/*` 和 `packages/*`，建立最小工作区。

### 3. App Router（应用路由器）

**专业解释：**

App Router 是 Next.js 基于 `app` 目录的路由系统，使用文件夹表达 URL 层级，并支持 Layout、Server Component 和嵌套路由。

**大白话：**

它类似 Vue Router 的“文件约定版”：目录结构本身就是路由配置，不需要先手写一张完整路由表。

**举例：**

`app/page.tsx` 对应首页；未来 `app/chat/page.tsx` 会对应 `/chat`。

**在 Jack AI Studio 中的作用：**

Web 端后续将用它组织 Dashboard、Chat、Knowledge 和 Agent 等页面。今天只保留初始化首页。

### 4. Frontend / Backend Boundary（前后端边界）

**专业解释：**

前后端边界用于明确浏览器端与可信服务端各自负责的逻辑、数据和安全职责。

**大白话：**

前端是用户能看到的店面，后端是保管密钥和处理业务的后厨。不能因为 Next.js 也能写服务端代码，就把所有 Python AI 服务职责混在 Web 项目中。

**举例：**

页面展示消息属于 `apps/web`；Provider API Key、模型调用和审计日志属于 `apps/api`。

**在 Jack AI Studio 中的作用：**

今天通过目录和 README 固化边界，避免后续重复实现 API 或把密钥暴露到浏览器。

## 项目实战

### 目录结构

```text
jack-ai-studio/
├── apps/
│   ├── web/      # Next.js Web 应用
│   └── api/      # Python API 服务（当前仅职责说明）
├── docs/
├── package.json
└── pnpm-workspace.yaml
```

### 常用命令

```bash
pnpm dev:web
pnpm lint:web
pnpm build:web
```

根脚本使用 `--filter` 精确调用 Web 包，后续增加其他应用时不需要改变现有命令语义。

## 关键代码说明

- 根 `package.json` 标记为 `private`，防止误发布整个仓库。
- `packageManager` 固定当前 pnpm 版本，降低不同开发环境产生差异的概率。
- `pnpm-workspace.yaml` 只声明工作区范围，不添加当前用不到的 catalogs、overrides 或构建编排。
- `apps/api` 今天没有 Python 业务代码，符合小步学习原则。

## 今日英文术语

1. **Monorepo**：单仓库多项目的代码组织方式。
2. **Workspace**：包管理器管理多个包的工作区能力。
3. **Package Manager**：包管理器，负责依赖和脚本。
4. **App Router**：Next.js 基于 `app` 目录的路由系统。
5. **Frontend**：运行在用户侧、负责交互和展示的前端。
6. **Backend**：运行在可信环境、负责业务和安全的后端。
7. **Dependency**：项目运行或开发所依赖的软件包。
8. **Build**：将源代码处理为可部署产物的构建过程。

## 遇到的问题

- `create-next-app` 首次在受限环境中无法写入用户级 pnpm dlx 缓存，授权后安装成功。
- 初始化器在 `apps/web` 生成了嵌套 workspace 和 lockfile；已合并为根目录唯一的 `pnpm-workspace.yaml` 与 `pnpm-lock.yaml`。
- `pnpm dev:web` 启动 Turbopack 后出现 `EMFILE: too many open files, watch`，随后访问首页返回 404。生产构建能够识别 `/`，production server 首页返回 HTTP 200，因此页面和路由本身正常；该问题记录为当前 Codex 运行环境的文件监听异常，后续需在本机终端复验开发模式。
- 异常 dev 过程生成了空的 `.next/dev/types/routes.d.ts`，使额外执行的独立 `tsc --noEmit` 与 production route types 冲突；`.next` 属于未提交的生成缓存，正式验收仍以已通过的 `next build` 内置 TypeScript 检查为准。
- 用户已在本机运行 `pnpm dev:web` 并确认页面访问正常，说明上述 watcher 和 404 只发生在 Codex 受限运行环境，不是项目代码问题。
