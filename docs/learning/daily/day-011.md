## 必备理论

### 1. Message（消息）

**专业解释：**

Message 是模型对话中的结构化输入单元，包含 Role 和 Content，而不只是一个普通字符串。

**大白话：**

聊天记录不能只保存“说了什么”，还要标明“谁说的”，模型才能正确理解指令和上下文。

**举例：**

```json
{
  "role": "user",
  "content": "用 Vue 类比 React State"
}
```

**在 Jack AI Studio 中的作用：**

后续前端输入、历史消息和 Provider 请求都会围绕统一 Message 结构传递。今天先建立 Schema，不发送到模型。

### 2. Message Role（消息角色）

**专业解释：**

Message Role 表示一条消息在模型上下文中的来源和语义职责。当前定义 `system`、`user`、`assistant`。

**大白话：**

它像企业群聊里的身份标签：系统规则、用户提问和模型回答不能混成没有来源的一堆文本。

**举例：**

| Role | 当前职责 |
| --- | --- |
| `system` | 给出整体行为、语气和任务背景 |
| `user` | 表示用户输入 |
| `assistant` | 表示模型历史回答 |

**在 Jack AI Studio 中的作用：**

它让 Provider 能按正确顺序构建上下文。`system` 不是管理员权限，也不能单独防止 Prompt Injection。

### 3. Chat Request（对话请求）

**专业解释：**

Chat Request 是一次模型推理输入的结构化集合，当前包含模型标识、消息列表和 Temperature。

**大白话：**

它像一张完整订单：不仅要写问题，还要说明交给哪个模型、带上哪些上下文、允许多大随机程度。

**举例：**

```python
ChatRequest(
    model="demo-model",
    messages=[
        ChatMessage(role="user", content="你好"),
    ],
)
```

**在 Jack AI Studio 中的作用：**

今天它是后端内部可信数据模型；后续 Chat Endpoint 接收请求后，会把它交给 Provider。

### 4. Temperature（温度）

**专业解释：**

Temperature 是调整模型 Token 采样概率分布的生成参数，影响输出的稳定性和多样性。

**大白话：**

它可以先理解为“随机发挥程度”：较低通常更稳定，较高通常更多样，但不是正确率或创造力的绝对开关。

**举例：**

当前 Schema 默认值为 `0.7`，只接受 `0～2`。

**在 Jack AI Studio 中的作用：**

后续 Provider 调用会读取该参数。不同模型的真实支持范围可能不同，未来由 Provider 适配层处理。

### 5. Data Contract（数据契约）

**专业解释：**

Data Contract 规定模块之间交换数据时必须遵守的字段、类型、枚举值和约束。

**大白话：**

它类似前后端接口文档加上真正执行的表单校验规则，不能只靠口头约定。

**举例：**

`messages` 至少一条、`content` 不能为空、`role` 只能来自 `MessageRole`。

**在 Jack AI Studio 中的作用：**

它连接未来的 Web、FastAPI Route、Chat Service 和 Provider，避免每层各自猜测消息格式。

## Python 学习

### StrEnum（字符串枚举）

`StrEnum` 用一组有限的字符串值表达业务状态：

```python
class MessageRole(StrEnum):
    SYSTEM = "system"
    USER = "user"
    ASSISTANT = "assistant"
```

它类似 TypeScript：

```ts
type MessageRole = "system" | "user" | "assistant"
```

普通 `str` 可以接收任意字符串；`StrEnum` 会让 Pydantic 在运行时拒绝 `"visitor"` 等未知角色。

## 项目实战

### 当前数据边界

```text
普通 dict
   ↓ Pydantic model_validate
ChatRequest
├── model: 非空字符串
├── messages: 至少一条 ChatMessage
│   ├── role: system | user | assistant
│   └── content: 非空字符串
└── temperature: 0～2，默认 0.7
```

### 今天没有发生的链路

```text
ChatRequest
   ✕ 没有 Chat Endpoint
   ✕ 没有 Provider
   ✕ 没有 API Key
   ✕ 没有真实模型响应
```

明确“尚未实现什么”可以防止把 Schema 校验误认为 AI Chat 已经可用。

## 关键代码说明

- `MessageRole` 继承 `StrEnum`，既限制允许值，也保留 JSON 友好的字符串形式。
- `ChatMessage` 把 Role 与 Content 组合成最小消息单元。
- `ChatRequest.messages` 使用 `Field(min_length=1)` 拒绝空对话。
- `temperature` 使用 `ge=0` 与 `le=2` 建立数值边界。
- 当前只定义输入模型，没有提前猜测 Provider Response Schema。
- 测试覆盖正常序列、默认值和四类无效边界。
- Chat 页面只展示“契约已建立、Provider 未接入”，没有启用输入框或假响应。

## 今日英文术语

1. **Message**：发送给模型的一条结构化消息。
2. **Role**：消息在上下文中的身份和语义职责。
3. **System Message**：描述整体行为和任务背景的消息。
4. **User Message**：表示用户输入的消息。
5. **Assistant Message**：表示模型历史回答的消息。
6. **Chat Request**：一次对话推理的结构化输入。
7. **Data Contract**：模块之间交换数据时必须遵守的契约。
8. **Enum**：只允许有限候选值的数据类型。
9. **Temperature**：影响模型采样随机程度的参数。
10. **Prompt Injection**：利用输入尝试改变或绕过模型指令的攻击方式。
