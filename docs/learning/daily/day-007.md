## 必备理论

### 1. Runtime Validation（运行时校验）

**专业解释：**

Runtime Validation 是在程序执行期间，检查实际输入是否符合类型、必填项和字段约束的过程。

**大白话：**

Type Hints 像表单旁写着“这里应该填手机号”，Runtime Validation 像点击提交时真正检查手机号格式。只有说明没有校验，错误数据仍可能进入程序。

**举例：**

`name: str` 是类型提示；`Field(min_length=1)` 会在运行时拒绝空字符串。

**在 Jack AI Studio 中的作用：**

后续模型配置、Chat 消息和工具参数都来自程序边界之外，不能只相信调用方。今天先为服务状态建立最小校验边界。

### 2. Pydantic

**专业解释：**

Pydantic 是使用 Python Type Hints 定义数据模型，并提供数据解析、运行时校验和序列化能力的第三方库。

**大白话：**

可以把它理解成 TypeScript 类型与 Zod 的组合：类型让编辑器看懂结构，Pydantic 再检查运行时收到的真实数据。

**举例：**

```python
service_status = ServiceStatus.model_validate(raw_data)
```

校验成功会得到 `ServiceStatus` 实例；失败会抛出 `ValidationError`。

**在 Jack AI Studio 中的作用：**

Pydantic 会成为 Python 后端 Schema 的基础。今天只独立学习它，后续 FastAPI 会复用相同模型校验 HTTP 请求和响应。

### 3. Schema（数据结构契约）

**专业解释：**

Schema 描述数据包含哪些字段、每个字段的类型及其约束，是数据生产者和消费者共同遵守的契约。

**大白话：**

它类似企业后台表单配置：不只是说有“名称”字段，还会规定必填、最小长度和数据类型。

**举例：**

`ServiceStatus` 规定 `name`、`status`、`python_version` 都不能为空，`planned_capabilities` 至少有一项。

**在 Jack AI Studio 中的作用：**

未来前端、API 路由、业务服务和 Provider 都要靠明确的 Schema 传递模型配置、消息和结果。

### 4. BaseModel 与 Field

**专业解释：**

`BaseModel` 是 Pydantic 数据模型的基类；`Field` 为字段补充最小长度等约束和元数据。

**大白话：**

`BaseModel` 像 Vue 表单的数据对象框架，`Field` 像每个表单项的校验规则。

**举例：**

```python
class ServiceStatus(BaseModel):
    name: str = Field(min_length=1)
```

**在 Jack AI Studio 中的作用：**

今天它们用于定义服务状态；后续会用于请求参数、响应结构和配置模型。

### 5. ValidationError（校验错误）

**专业解释：**

`ValidationError` 是输入数据无法通过 Pydantic 模型校验时抛出的异常，其中保存字段位置、错误类型和说明。

**大白话：**

它会明确告诉我们“哪几个表单项错了”，而不是只返回一句模糊的“数据不合法”。

**举例：**

空 `name` 和空 `planned_capabilities` 会分别形成一条错误记录。

**在 Jack AI Studio 中的作用：**

今天在终端观察错误字段；未来 API 层会把它转换为客户端可理解的错误响应。

## Python 学习

### TypeScript / Zod 与 Python / Pydantic 对照

| 前端经验 | Python 后端 |
| --- | --- |
| TypeScript `interface` | Python Type Hints |
| Zod `z.object(...)` | Pydantic `BaseModel` |
| `.min(1)` | `Field(min_length=1)` |
| `schema.parse(data)` | `Model.model_validate(data)` |
| `ZodError` | `ValidationError` |

### Type Hints 与 Pydantic 的职责

```text
普通 dict
   ↓
Type Hints：帮助编辑器和静态检查器理解预期类型
   ↓
Pydantic：在运行时检查真实值和字段约束
   ↓
可信的 ServiceStatus 实例
```

Type Hints 不是无用的：Pydantic 正是读取这些类型信息来建立校验规则。两者是配合关系，不是替代关系。

## 项目实战

### 依赖管理

根目录新增：

```text
pyproject.toml  # 声明 Python 版本和直接依赖
uv.lock         # 锁定完整、可复现的依赖版本
```

当前只新增一个直接依赖：

```toml
dependencies = [
    "pydantic>=2.13.4",
]
```

### 数据流

```text
SERVICE_INFO + PLANNED_CAPABILITIES
                  ↓
        build_service_status()
                  ↓ model_validate
      成功：ServiceStatus 实例
      失败：ValidationError
                  ↓
       format_service_status()
                  ↓
               终端
```

### 运行

在仓库根目录执行：

```bash
uv run python apps/api/app/main.py
```

预期第一行输出通过校验的服务状态，第二行说明错误示例中的 `name` 和 `planned_capabilities` 已被拒绝。

## 关键代码说明

- `ServiceStatus` 继承 `BaseModel`，把数据结构升级为运行时可验证的 Schema。
- `Field(min_length=1)` 同时约束字符串不能为空、列表至少有一项。
- `model_validate(...)` 是普通 `dict` 进入可信模型的边界。
- `format_service_status(...)` 只接收已校验模型，不再直接相信普通 `dict`。
- `except ValidationError` 只处理预期的校验错误，没有用宽泛的 `except Exception` 隐藏其他 Bug。
- `pyproject.toml` 声明直接依赖，`uv.lock` 固定本次解析出的完整依赖树。

## 今日英文术语

1. **Runtime Validation**：程序运行期间检查真实输入。
2. **Pydantic**：基于 Type Hints 的 Python 数据校验库。
3. **Schema**：字段、类型和约束组成的数据结构契约。
4. **BaseModel**：Pydantic 数据模型基类。
5. **Field**：字段约束和元数据声明。
6. **Constraint**：数据必须满足的约束。
7. **ValidationError**：数据校验失败时产生的异常。
8. **Dependency**：项目运行依赖的外部软件包。
9. **Lockfile**：固定完整依赖解析结果的锁文件。
10. **Serialization**：把模型转换为 JSON 等可传输形式的序列化过程。
